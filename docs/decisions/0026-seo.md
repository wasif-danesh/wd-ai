# ADR-0026: SEO and discoverability

- **Status:** Proposed (planning record; not scheduled)
- **Date:** 2026-10-08

## Context

The app is behind a stub user today and every page is private. A public product needs pages that
search engines and social previews can read, without exposing user content that should stay private.

## Decision (proposed)

- **Public vs private pages.** Public: landing, pricing, docs and an optional shareable song page
  (only when the owner chooses to share). Private (`noindex`): "My songs", create flow, admin, auth.
- **Next.js built-ins.** Server-rendered pages, the Metadata API (title, description, canonical),
  `sitemap.ts`, `robots.ts`, and generated Open Graph and Twitter images (the song cover for a
  shared song page).
- **Structured data.** JSON-LD (`WebApplication` for the landing page, `MusicRecording` for shared
  songs).
- **Performance** counts as SEO: keep Core Web Vitals in budget (`next/image`, font loading, no
  layout shift); check in CI with Lighthouse on the public pages.
- **Shared songs** get a unguessable ID, a visible owner opt-in and a takedown path (links to the
  moderation and legal items in the roadmap).
- **Per-product config.** Each product supplies its metadata (name, description, images) so a new
  product does not touch platform code.
- **Multi-language** (hreflang) is out of scope until the app is translated.

## Consequences

- Public song pages are the first place user content leaves the account: sharing needs an explicit
  setting, moderation of what is shown, and a privacy review.
- Authentication must exist before sharing, so the owner can be identified.
